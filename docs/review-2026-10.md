# cornerGuider – Review und Arbeitsauftrag (Stand 19.10.2026)

Dieses Dokument ist ein Arbeitsauftrag für Claude Code. Es beschreibt Auffälligkeiten aus einer Projekt-Review und sagt, was geändert werden soll. Ablageort im Repo: `docs/review-2026-10.md`.

## 0. Grundregeln für diese Runde

**Feature-Stopp.** In dieser Runde werden keine neuen Komfortfunktionen gebaut. Erlaubt sind nur die Aufgaben in Abschnitt 2. Alles in Abschnitt 4 („Nicht jetzt") wird nicht angefasst, auch nicht teilweise.

Arbeitsweise:

1. Vor jeder Aufgabe den betroffenen Code lesen und kurz zusammenfassen, wie er heute funktioniert. Die Review kennt den Code nicht im Detail; wenn eine Annahme in diesem Dokument nicht zum Code passt, **anhalten und nachfragen**, statt die Annahme durchzudrücken.
2. Für Logik in `src/` zuerst Tests schreiben (Jest), dann implementieren.
3. Nach jeder Aufgabe `npm test` und `npm run typecheck` ausführen. Beide müssen grün sein.
4. Eine Aufgabe = ein Commit mit klarer Nachricht (z. B. `feat(curves): tightening/opening detection`).
5. Neue Pakete **nur** mit `npx expo install`. Projekt bleibt auf Expo SDK 54.
6. `expo prebuild` nur mit `--clean`.
7. Alle neuen Texte in `src/i18n/dictionary.ts`, immer Deutsch **und** Englisch.
8. Nichts als „getestet" bezeichnen, was nur im Simulator oder gar nicht lief. Den Abschnitt „Nicht geprüft" in `README.md` nach jeder Aufgabe aktualisieren.
9. Keine Dateien außerhalb des Repos löschen oder verschieben.

## 2. Aufgaben (in dieser Reihenfolge)

### A1 – Konfidenz pro Ansage und hörbares Unsicherheitssignal (B3, B4)

**Ziel:** Der Fahrer weiß jederzeit, ob die App etwas sieht oder nicht.

Änderungen:

- Jede erkannte Kurve bekommt einen Wert `confidence` (0–1). Er sinkt mindestens bei:
  - großem Abstand zwischen den **originalen** Knoten der Geometrie im Kurvenbereich (vor dem Resampling auf 5 m), also grob gezeichneten OSM-Straßen,
  - Vorhersage in der Freien Fahrt nahe einer unklaren Kreuzung,
  - schlechter GPS-Genauigkeit oder Off-Route-Zustand.
  Die Schwellwerte dafür kommen nach `src/curves/config.ts`, mit Kommentar, dass sie geschätzt sind.
- Liegt die Konfidenz unter einem Schwellwert, wird die Kurve **nicht mit Stufe** angesagt, sondern als „Kurve, unsicher" (Englisch: „Curve, uncertain").
- Neues Ereignis „Vorhersage endet": Wenn die Freie Fahrt die Vorhersage abbricht (Kreuzung, keine Daten, kein Netz ohne Kacheln), kommt **einmal** ein eigener kurzer Hinweis, z. B. „Keine Vorschau" / „No preview". Wenn die Vorschau wieder da ist: „Vorschau wieder da" / „Preview back". Kein Dauerwiederholen.
- Im Display: unsichere Kurven sichtbar anders darstellen (z. B. gestrichelt, Stufe ausgegraut).

**Fertig, wenn:**
- Tests decken ab: grobe Geometrie → niedrige Konfidenz; feine Geometrie → hohe Konfidenz; Abbruch der Vorhersage löst genau ein Ereignis aus.
- Die CLI `npm run curves -- datei.gpx` gibt die Konfidenz pro Kurve mit aus.

### A2 – Sicherheitsausrichtung der Schwellwerte (B2, B4)

**Ziel:** Solange nichts kalibriert ist, lieber zu streng als zu mild.

Änderungen:

- In `src/curves/config.ts` einen klar benannten Parameter einführen (z. B. `safetyMarginRadiusFactor`), der den gemessenen Radius vor der Einstufung leicht verkleinert. Standardwert so, dass eine Grenzkurve eher eine Stufe enger eingestuft wird.
- Bei niedriger Konfidenz (aus A1) zusätzlich eine Stufe enger einstufen, falls doch eine Stufe angesagt wird.
- Die Messung auf Stelvio und Amalfi wiederholen und die Ergebnisse vorher/nachher in `README.md` eintragen.

**Fertig, wenn:**
- Regressionstests mit den vorhandenen GPX-Dateien von Stelvio und Amalfi existieren, die die Anzahl erkannter Kurven und die Verteilung der Stufen festhalten, damit spätere Änderungen sichtbar werden.
- Keine Zahl im README wurde geschönt; Verschlechterungen werden genauso eingetragen.

### A3 – „Zieht zu" / „öffnet sich" (B5)

**Ziel:** Die wichtigste Zusatzinformation für Motorradfahrer.

Änderungen:

- Für jedes Kurvensegment den Radiusverlauf über die 5-m-Stützpunkte auswerten (Radius am Anfang vs. engster Punkt vs. Ende, geglättet).
- Neues Feld am Kurvenobjekt, z. B. `radiusTrend: 'tightening' | 'opening' | 'constant'`. Schwellwerte in `config.ts`.
- Ansage erweitern: „Rechts 3, zieht zu" / „Right 3, tightens"; „Links 4, öffnet" / „Left 4, opens". Bei `constant` keine Ergänzung.
- „Zieht zu" darf durch den Ansagefilter („ab Stufe") **nicht** unterdrückt werden: Eine zuziehende Kurve wird immer angesagt, auch wenn ihre Einstiegsstufe unter dem Filter liegt.
- Grafik: zuziehende Kurve sichtbar markieren.

**Fertig, wenn:**
- Tests mit synthetischen Geometrien: Kreisbogen konstant, Spirale mit abnehmendem Radius, Spirale mit zunehmendem Radius. Jeweils richtige Einstufung.
- Die CLI gibt den Trend aus. Auf Stelvio stichprobenartig 5 Kurven prüfen und das Ergebnis im Commit beschreiben.

> Klärung (Max, 19.10.2026): Im Code existiert bereits `shape` (tightening/opening/constant) mit Ansage „zieht zu". Statt eines neuen Feldes `radiusTrend` wird `shape` weiterverwendet.

### A4 – Fahrtaufzeichnung für die Kalibrierung (B1, B10)

**Ziel:** Jede echte Fahrt im Frühjahr liefert automatisch Kalibrierdaten. In dieser Runde **nur aufzeichnen und auswerten**, die App ändert ihre Schwellwerte nicht selbst.

Änderungen:

- Die vorhandene Aufzeichnung (Freie Fahrt / Feedback-Export) um pro Messpunkt erweitern: Zeit, Position, GPS-Geschwindigkeit, GPS-Genauigkeit, und falls verfügbar Rollwinkel aus `expo-sensors` (DeviceMotion). Paket mit `npx expo install expo-sensors`.
- Die Halterung am Lenker ist unbekannt ausgerichtet. Deshalb:
  - Beim Start der Fahrt im Stand einen Nullpunkt aufnehmen.
  - Zusätzlich die **rechnerische** Schräglage aus Geschwindigkeit und Radius ablegen: `atan(v² / (r · g))`. Sie ist die Rückfallgröße, wenn der Sensorwert unbrauchbar ist.
- Neues CLI-Skript `npm run calibrate -- aufzeichnung.json`: ordnet jede gefahrene Kurve der vorhergesagten Kurve zu und gibt eine Tabelle aus (vorhergesagte Stufe, Radius, gefahrene Geschwindigkeit, gemessene und rechnerische Schräglage, Trend).
- Die Knöpfe „Falsch"/„Fehlt" bleiben, werden aber nicht weiter ausgebaut.

**Fertig, wenn:**
- Aufzeichnungsformat ist versioniert (`schemaVersion`) und in `docs/` beschrieben.
- `calibrate` läuft mit einer simulierten Fahrt aus dem Simulationsmodus durch.
- Datenschutz: Aufzeichnung bleibt auf dem Gerät, Export nur aktiv durch den Nutzer. Den Entwurf der Datenschutzerklärung in `docs/release/` entsprechend ergänzen und als Entwurf kennzeichnen.

### A5 – Zusammenspiel mit Navigations-Apps (B9)

**Ziel:** cornerGuider läuft neben Kurviger, Calimoto oder Google Maps, ohne zu stören.

Änderungen:

- Den aktuellen Stand der Audio-Session auf iOS und des Audio-Fokus auf Android dokumentieren (wer duckt wen, was passiert, wenn eine andere App gerade spricht).
- Ansagen kürzen, wo möglich. Neue Einstellung „Kurze Ansagen" (nur Richtung und Stufe, kein Vorlauf-Text wie „In 240 m").
- Prüfen, ob die Ortung sparsamer laufen kann (Genauigkeit/Intervall abhängig von Geschwindigkeit). Nur umsetzen, wenn die Tracker-Tests weiter grün sind.
- Ein manuelles Testprotokoll anlegen: `docs/test-protocol-navi.md` mit Schritten für iOS und Android (Navi-App + cornerGuider parallel, Bluetooth-Headset, 30 min Fahrt, Akkustand vorher/nachher, Überlagerungen notieren). Claude Code kann diesen Test nicht selbst durchführen und darf ihn nicht als erledigt markieren.

**Fertig, wenn:**
- Dokumentation und Einstellung sind vorhanden, Testprotokoll liegt bereit.

### A6 – Straßendaten-Quelle austauschbar machen und Backend planen (B6, B7)

**Ziel:** Kein Release mit öffentlichen Overpass-Servern als Backend.

Änderungen:

- Eine Schnittstelle einführen, z. B. `RoadDataSource`, hinter der Overpass, Offline-Kacheln und ein späteres eigenes Backend austauschbar sind. Die Freie Fahrt nutzt nur noch diese Schnittstelle.
- Server-URL konfigurierbar (Build-Konfiguration), eindeutiger `User-Agent`, Begrenzung der Anfragen pro Minute, Caching.
- Neues Dokument `docs/road-data-backend.md` mit zwei Optionen, jeweils Aufwand, Kosten, Wartung:
  1. Eigener Overpass-Server (Docker) mit OSM-Extrakt für Deutschland und die Alpen.
  2. Vorberechnete Straßenkacheln aus einem OSM-PBF-Extrakt, die die App herunterlädt.
  Mit Empfehlung, aber **ohne** Umsetzung in dieser Runde.
- OSM-Namensnennung („© OpenStreetMap-Mitwirkende", Link auf die Lizenz) in Einstellungen/Über und auf der Freie-Fahrt-Anzeige ergänzen. Store-Texte und Website-Briefing um denselben Hinweis ergänzen.

**Fertig, wenn:**
- Bestehende Tests der Freien Fahrt laufen über die neue Schnittstelle grün.
- Ein Mock-`RoadDataSource` für Tests existiert.

### A7 – Store-Builds über EAS (B8)

Änderungen:

- `eas.json` prüfen: Profile `development`, `preview` (interne Verteilung) und `production`.
- In `docs/release/checklist.md` festhalten: Uploads in App Store Connect nur aus EAS-Cloud-Builds, nie lokal mit Xcode 16.4.
- Prüfen, ob das Live-Activity-Ziel von `expo-live-activity` beim Prebuild in der Cloud korrekt entsteht (Config-Plugin, keine lokal von Hand angelegten Dateien, die nicht im Repo sind). Ergebnis dokumentieren.
- Builds nicht selbst auslösen, wenn dafür Anmeldung oder Bezahlung nötig ist; stattdessen die genauen Befehle in die Checkliste schreiben.

### A8 – Android 13+ Benachrichtigungsrecht (B11)

Änderungen:

- Vor dem Start des Fahrmodus `POST_NOTIFICATIONS` anfragen (Android 13+). Bei Ablehnung einen klaren Hinweis zeigen, dass die Ortung im Hintergrund unzuverlässig sein kann.
- Text in beiden Sprachen.
